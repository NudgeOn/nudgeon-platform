# 로컬 운영 부하·복구 검증 — 2026-09-03

## 결론

**복구 시험은 통과했지만, 운영 부하·경보 검증은 아직 통과하지 못했다.**
초당 200건의 짧은 시험은 성공했다. 초당 500건 및 100건/초 5분 시험은
실패했다. 이를 제품의 최대 처리량으로 해석하면 안 된다. 부하 발생기의
연결 재사용 결함, 제한된 로컬 자원, 다른 프로젝트와의 자원 공유가 있다.

## 재현된 결함과 운영상 문제

### OPS-01 — 부하 발생기가 HTTP 연결을 재사용하지 않음

`apps/worker/cmd/loadgen/main.go:321`에서 응답 본문을 읽지 않고 닫는다.
실제 `postTrack` 함수에 가짜 HTTP 서버를 연결한 독립 시험에서
**연속 10회 요청이 TCP 연결 10개를 생성**했다. 연결 1개 재사용을 기대한 시험은 실패했다.
생산 서비스로 이벤트를 보내지 않는 재현 시험이다.

대응: 응답 본문을 안전하게 소비하고 연결 재사용을 검증한 뒤 부하 재시험.
이 결함이 500건/초 실패 전부를 설명한다고 단정하지 않는다.

### OPS-02 — 첫 DLQ 항목의 경보 누락

실제 worker가 DLQ를 기록하고 기존 `deploy/observability/alerts.yml` 규칙을
Prometheus → Alertmanager → 로컬 webhook으로 실행했다.

- 첫 항목 기록: 2026-09-03 07:57:18 KST. 이후 20초 동안 경보·수신 모두 0.
- 두 번째 기록: 07:57:39. 경보 수신: 07:57:43.
- 신규 실패가 없는 5분 뒤 08:02:42에 resolved 알림 수신.
  DLQ 2개를 재처리했다는 뜻은 아니다.

CounterVec 라벨은 첫 증가 때 생성된다. 최초 관측값이 이미 1이면
`increase(...[5m]) > 0`은 첫 항목을 증가로 잡지 못하는 조건이 생긴다.
대응: 초기값·재시작·첫 항목 조건을 포함한 지표/규칙 및 경보 회귀 시험 보완.

실험에서는 테스트 전용 손상된 credential과 재시도 횟수 4를 주입했다.
worker가 다음 실패를 실제 처리해 DLQ와 metric을 기록했다.
자연스럽게 5회 재시도하는 전 과정이나 실제 공급자 실패는 시험하지 않았다.
손상 credential fixture만 제거했으며 실제 사용자 데이터는 삭제하지 않았다.

### OPS-03 — API 정상 종료가 20초 안에 완료되지 않음

아래는 최초 발견 당시 기록이다. 후속 수정과 실제 종료·접수 보존 검증은
[P0-3 API 종료 QA](API-SHUTDOWN-QA-2026-09-03.md)를 참조한다. 이전 부하 수치는 갱신하지 않았다.

원본 API와 복원 API 모두 `docker compose stop -t 20` 후 exit 137,
`OOMKilled=false`였다. worker는 exit 0이었다.
API에는 `enableShutdownHooks()`가 있으므로 훅 누락이라고 단정할 수 없다.
연결·종료 훅의 대기를 조사하고 정상 종료 시간 및 진행 중 요청 처리 시험이 필요하다.

### 장시간 시험 전 해결할 제한

- CH 1 GiB 제한에서 메모리 오류와 재시도가 발생했다. 다른 프로젝트를 유지한
  로컬 자원 배분 조건이다. 메모리·배치·저장 패턴을 조정하고 다시 측정해야 한다.
- loadgen은 지연 샘플 3종을 전부 메모리에 보관한다.
  5,000건/초 × 24시간이면 4억 3,200만 요청이며, duration 원소만 약 10.4 GB다.
  배열 여유·정렬 복사·기타 데이터는 별도다. 이는 소스 기반 계산이며 실측이 아니다.
- 고정 사용자 풀, bounded histogram, 전송/응답 ID 기록, 저장소 대사,
  데이터 보존·디스크 예산을 갖춘 뒤 24시간 시험을 실행해야 한다.

# API 키 갱신 병목 QA — P1-2a · 2026-09-03

**키 사용 시각의 불필요한 갱신을 줄였고, 잠금 격리·인증·접수 대사를 검증했다.
100 TPS 지속 성능은 아직 통과하지 못했다.** 기존 실행 서비스는 변경하지 않았다.

## 무엇을 수정했나

기존에는 모든 인증 요청이 `api_keys.last_used_at`을 비동기로 갱신했다. 응답을 기다리지
않더라도 이벤트 저장과 같은 10개짜리 접속 풀을 사용하므로, 같은 키 행을 기다리는 쓰기가
풀 전체를 점유할 수 있었다. 실제 잠금 실험에서 이를 재현했다.

`API_KEY_USAGE_COALESCE_ENABLED=true`일 때 사용 시각만 DB 시각 기준 60초 간격으로
묶는다. 같은 키 1개, 전체 API 프로세스당 최대 2개의 미완료 기록 작업만 허용한다.
DB 조건도 재검사하므로 서로 다른 API 인스턴스의 동시 갱신은 실제 행 변경 1건으로 수렴한다.
오래된 SELECT 결과로 UPDATE가 추가 실행돼도 조건 불일치 `noop`이면 실제 행을 바꾸지 않는다.

키 유효성·scope·폐기·회전 만료는 **매 요청 DB 조회**를 유지한다. 인증 캐시가 아니다.
사용 시각은 best-effort 표시 정보이며 감사 기록이나 엄격한 60초 최신성 보장이 아니다.
예산 초과·DB 오류는 기록을 생략하고 다음 요청에서 재시도한다. 접수/outbox COMMIT 계약,
사용자 cursor/profile 잠금 순서, 풀 크기 10, `synchronous_commit`은 변경하지 않았다.

기본값/롤백은 `false`다. 루트·배포 환경 예시와 Compose에 선택적 설정을 추가했지만,
기존 서버의 설정을 바꾸거나 재시작하지 않았다. [계측 정의](INGESTION-METRICS.md) 참고.

## 실제 잠금 재현

시험 키 행을 별도 transaction으로 잠그고, 새 이벤트 20개를 실제 HTTP로 보냈다.

| 동일 이미지의 설정 | 키 갱신 때문에 잠금 대기한 접속 | 잠금 해제 전에 완료된 요청 | 해제 후 PG / CH |
| --- | ---: | ---: | ---: |
| 기존 방식 `false` | 10개 | 3 / 20 | 20 / 20 |
| 수정 방식 `true` | 1개 | 20 / 20 | 20 / 20 |

수정 방식은 메타데이터 행이 잠겨 있어도 이벤트를 접수했다. 각 lane의 승인 ID가 PG 원장,
projected marker, CH **물리 행**과 정확히 일치했다. 이 실험은 의도한 잠금 장애 lane이며,
일반 요청의 p99 측정이나 실제 운영 장애 빈도를 의미하지 않는다.

## 일반 부하: 좋은 결과와 실패를 모두 기록

동일 API 이미지·풀·DB·워커에서 **off → on → on → off** 순서로 비교했다.
매 회 새 API 프로세스와 합성 키, 새 익명 사용자/기기/이벤트 1개씩, 요청자 20개,
100 req/s·10초·예정 1,000건이다. DB/CH/worker는 회차 사이 유지했다.
긴 준비 구간/M0/M1 데이터는 없으므로 G1 시험이 아니다.

| 회차 | 설정 | 구간 내 성공 | 종료 후 성공 | 발생기 드롭 = 실패 | 종단 p99 | 게이트 |
| --- | --- | ---: | ---: | ---: | ---: | --- |
| 1 | 기존 | 1,000 | 0 | 0 | 9.343ms | PASS |
| 2 | 수정 | 1,000 | 0 | 0 | 17.535ms | PASS |
| 3 | 수정 | 786 | 60 | **154** | **1,547.263ms** | **FAIL** |
| 4 | 기존 | 1,000 | 0 | 0 | 78.335ms | PASS |

HTTP/네트워크/응답 오류는 네 회차 모두 0이다. 하지만 발생기에서 버린 154건은
`failed_total=154`에 포함됐다. 3회차를 `846/10=84.6 TPS 성공`으로 발표하지 않는다.
측정 구간 내 성공은 **78.6 req/s**이며, 99% 목표 처리율과 500ms p99 기준도 실패했다.
좋은 회차만 선택하거나 최대 TPS/응답 속도 개선을 주장할 수 없다.

| 회차 | 실제 인증 SELECT | 사용 시각 UPDATE 호출 / 변경 행 | 해당 UPDATE의 WAL bytes | 승인 = PG = projected = CH 물리 행 |
| --- | ---: | ---: | ---: | ---: |
| 1 기존 | 1,000 | 1,000 / 1,000 | 80,156 | 1,000 |
| 2 수정 | 1,000 | 2 / **1** | 86 | 1,000 |
| 3 수정 | 846 | 1 / **1** | 86 | 846 |
| 4 기존 | 1,000 | 1,000 / 1,000 | 81,024 | 1,000 |

완주한 수정 회차에서 **사용 시각 행 갱신은 99.9% 감소**했다. 모든 SQL이나 전체 WAL이
99.9% 줄었다는 뜻은 아니다. 다른 SQL의 WAL은 회차당 약 7–8MB였고 일반 부하의 p99는
일관되게 좋아지지 않았다. 총 부하 승인 **3,846건**과 잠금 lane **40건**의 정확한 ID/행 대사는
통과했다. 실패 154건은 DB에 보냈다고 가정하지 않으며 미전송과 저장 유실을 구분한다.

## 남은 병목의 관측

3회차 API 표본 46개에서 pool 대기 최대 10개를 관측했다. 해당 회차의 API receipt
`pool_acquire` 누적은 **11.840초/846회**, `commit` 왕복 누적은 **8.125초/846회**였다.
이는 병렬 요청 누적 시간이며 실경과 시간이나 p99가 아니다.

COMMIT 중 `LWLock/WALWrite` 22, `IO/WALSync` 4, `IO/WALInitSync` 1개의
접속-표본 관측이 있었다. 해당 이벤트는 WAL 쓰기·동기화 대기이며 의미는
[PostgreSQL 16 대기 이벤트 문서](https://www.postgresql.org/docs/16/monitoring-stats.html)를 따른다.
표본 합계를 대기 초나 서로 다른 장애 건수로 해석하지 않는다.
`pg_stat_statements`의 COMMIT 실행 통계와 클라이언트 COMMIT 왕복은 같지 않으므로
서버의 짧은 statement 통계만 보고 커밋 지연이 없다고 결론 내리지 않는다.

키 쓰기가 이미 1건뿐인 회차에서도 실패했으므로 **이 변경만으로 병목 전체를 해결할 수 없다**.
WAL/디스크·가상화·다른 프로세스의 자원 경합·transaction 수를 다음에 분리 관측해야 한다.
호스트는 14코어, 기존 실행 컨테이너 19개, 시작 load average 약 22.3/36.2/37.7이었다.
어느 하나를 단독 근본 원인으로 확정하지 않는다. 디스크 내구성을 낮추는 설정은 적용하지 않았다.

## 회귀·실험 오류와 빌드 경계

- 기본 API: **163 통과**, 환경 의존 통합 **18 기본 스킵**. 타입 검사·저장소 규칙 통과.
- 추가 단위 회귀 8건: 같은 키 합치기, 서로 다른 키 예산, 최근 기록 생략, false 롤백,
  실패 후 예산 회수, 매 요청 scope/폐기 조회, 회전 만료, 잘못된 키/DB 오류 거부.
- 실제 PG: 키 기록/인증 4건 + 기존 receipt 7건 = **11 통과·스킵 0**.
  독립 두 인스턴스 조건 재검사, 61초 경과 갱신, 폐기/scope/회전 만료를 포함한다.
- 첫 실행 `9f3c557a`는 시험 입력의 `anonymous_id` 오타로 HTTP 400을 받아 중단했다.
  계약에 맞는 `anon_id`로 수정했다. 실패 실행은 성능 결과로 사용하지 않고 보존했다.
- 부하 실행 `fc747859`의 테스트 본문은 11개 통과했지만, 뒤의 fixture 정리에서 FK 오류로
  suite 전체가 실패했다. FK가 cascade라고 가정한 시험 코드를 고쳐 키 → 앱 → 고객사 순으로
  시험 소유 행만 제거했다. 새 PG `4dc1fbc1`에서 정리 hook까지 포함해 **11/11 재검증**했다.
  부하 결과를 바꾸려고 네 회차를 다시 돌리지는 않았다. 원본 runner `pass=false`는 그대로다.
- 부하/잠금 시간: **18:54:55–18:56:07 KST**. 별도 PG 재검증: **18:57:42–18:57:48 KST**.
- API 전체 Dockerfile로 만든 이미지:
  `sha256:6fe6ad20e5451f626db8f9e50cd82fb774e5d7e60542e09eea87125af049f4fb`.
  첫 실행의 새 빌드를 두 번째 실행에서 재사용했다. source label과 매 회 실행 image ID를 확인했다.
- 빌드 기준 HEAD `0f4f28141af0e7d3544c548a69bf3b784e5cfc0b`, dirty 상태 보존.
  299개 파일의 source SHA:
  `47e74171a8e7e9e8db0b9fbeb630510268517f12771787b2e19a648f98ca94c7`.
  이후 manifest 입력 중 변경된 파일은 **통합 테스트 정리 코드 1개뿐**이다.
  제품 코드는 부하 이미지와 같으며, 수정된 테스트가 들어간 전체 이미지를 재빌드했다고 하지는 않는다.
- worker는 이전 전체 빌드
  `sha256:d647831a9823235a5ab12088443c66c685b980184febedb4a100b431fe7e21fc`를 재사용했다.
  worker/shared Go/schema 입력 전체가 이전 manifest와 일치함을 확인했다. 새 worker 빌드가 아니다.
- 부하 시험 7개와 PG 재검증 2개 컨테이너 모두 exit 0·OOM 없음. 기존 19개 서비스 보존.
  시험 DB·이미지·증거는 유지하고 시험용 빈 네트워크만 해제했다.

Postgres 성능 스킬은 인증과 receipt lock 계약을 보존하며 불필요한 쓰기를 줄이는 데,
전체 흐름 검증 스킬은 실제 HTTP → PG → CH 대사와 실패 경계 분리에 적용했다.
사용 시각·시험 환경 변경은 UI 화면 변경이 아니며 이번에는 화면 캡처를 만들지 않았다.

## 구현 내용

1. 최근 5분의 counter 증가량 대신 DB의 `resolved_at IS NULL` 항목을 집계한다.
   재처리 큐 발행은 완료가 아니다. 같은 키가 다시 실패하면 해결 표시를 초기화한다.
2. `dlq-monitor`를 별도 역할로 추가했다. `all`에 포함하지 않으며 PG 외의 Redis·CH·발송 키가 필요 없다.
   조회 실패는 0건이 아니라 미확인으로 표시하고 마지막 성공값과 성공 시각을 보존한다.
3. 첫 조회 실패, 오래된 관측값, 모니터 중단·설정 누락을 별도 critical 경보로 표시한다.
   동일 DB의 관측자는 고유 cluster 라벨과 `max`로 중복 합계를 피한다.
4. 읽기 전용 연결 최대 1개, 조회 간격 5초, 쿼리/연결 timeout 2초를 적용했다.
   미해결 부분 인덱스 존재와 실제 observer 연결 **1개**를 격리 DB에서 확인했다.
   PostgreSQL 성능 스킬은 이 연결 제한·부분 인덱스·짧은 개별 resolve에 반영했다.
5. `dlq resolve`는 tenant UUID·행 UUID·조회한 created_at·근거·`--verified`를 요구한다.
   다른 tenant 또는 오래된 확인으로 새 실패를 완료 처리하지 못하도록 조건부 UPDATE한다.

배포 순서·상태 정의·운영 계정 분리는 [DLQ 런북](DLQ-RUNBOOK.md), 재현 명령은
[격리 시험 안내](../tests/ops/dlq/README.md)를 따른다. 운영 스키마·서비스에는 적용하지 않았다.

## 추가 발견 및 수정: 시험 수신기 종료

첫 시도 `nudgeon-dlq-qa-3013d84e`는 첫 경보 13.571초 및 330초 경보 유지 검사를 통과했지만,
정리 단계에서 Node 수신기만 **exit 137**, `OOMKilled=false`였다. 최초 runner의 `pass:true`는

수신기의 SIGTERM/SIGINT 처리와 HTTP/PG 소켓 종료를 추가하고, runner도 정지 상태뿐 아니라
모든 종료 코드가 0인지 검사하도록 수정했다. 새 프로젝트에서 위 전 과정을 다시 실행해
5개 모두 exit 0을 확인했다. **API 본체의 종료 결함(P0-3)을 수정한 것은 아니다.**

## 다음 수정과 검증 경계

**P0-2b: DLQ 저장 실패 후 ACK 위험을 먼저 수정해야 한다.** 코드 검토에서 push의
`retryFail → toDLQ` 및 공통 `SendLoop → handler.DLQ`가 저장 오류를 반환받지 않고
종결 상태로 진행하는 경로를 확인했다. message_log 저장이 성공하면 원본 큐가 ACK될 수 있다.
이번 SELECT 권한 회수 시험은 관측자 오류 시험이며, writer의 INSERT 실패 복구 검증은 아니다.
후속 회귀는 INSERT 실패 시 pending 유지 → DB 복구 → DLQ 저장 → 안전한 ACK를 검증해야 한다.

그 뒤 P0-3 API 정상 종료, P0-4 계측/이미지 증거, relay·ingest 개선과 단계별 부하 검증을 진행한다.
기존 replay 명령의 push 전용 라우팅, 단건 조회 tenant 범위, `--all` 무제한도 별도 미해결 항목이다.

1분을 넘는 모니터 관측 중단에서는 Entries가 해제될 수 있으므로 별도 observer 경보와
새로운 정상 DB 조회를 함께 확인해야 한다. Prometheus/Alertmanager 자체 장애와 외부 채널 수신은
이번 격리 시험의 보장 범위가 아니다.

지속 TPS·5,000 ev/s·24시간 soak·관리형 DB 복구·실제 단말 수신은 이번 결과로 갱신하지 않는다.
두 시도의 원본 로그/수신 내역은 ignored `.nudgeon/<project>/`에, 컨테이너·볼륨은 정지 상태로
남겼다. 데이터를 삭제하지 않았으며 테스트 이미지 태그도 덮어쓰지 않았다.

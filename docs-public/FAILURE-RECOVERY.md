# 실패 기록과 재발송

## 현재 제공하는 기록

- 콘솔 `/logs?status=failed`: 현재 필터에 맞는 최근 200건. 고객·기기·메시지 ID, 실패 분류와 상세 사유를 확인한다. 전체 실패 목록을 영구 보관하는 다운로드는 아니다. ClickHouse 보존 정책의 영향을 받는다.
- `/logs?test_run_id=<UUID>&status=failed`: 특정 테스트의 실패만 확인한다.
- PostgreSQL `test_push_runs`: 최근 테스트 이력을 서버에 저장한다. API는 최근 20건을 조회하며 요청 접수와 큐 발행을 구분한다. 수신 완료를 의미하지 않는다.
- PostgreSQL `send_dlq`: 자동 재시도를 소진한 메시지의 원본 envelope와 시도 횟수 등을 보관한다. 모든 `failed` 로그에 DLQ가 존재하는 것은 아니다.
- 운영자는 `go run ./apps/worker/cmd/dlq list --tenant <tenant-uuid> --limit 50`으로 DLQ를 조회할 수 있다. DB 연결 환경변수가 필요하다.

## 이번 변경으로 복구할 수 있는 것

설치 위자드에서 기기 한 대를 선택하고 발송 내용을 확인한다. 테스트 접수 시 `Idempotency-Key` UUID를 사용한다. 응답이 유실되면 **같은 요청 다시 확인**으로 동일한 요청 키와 내용을 보낸다. 서버는 기존 테스트·메시지 ID를 반환하고 새 outbox 작업을 만들지 않는다. 같은 키로 내용을 바꾸면 409다.

이는 **접수 결과 복구**다. 이미 실패한 발송을 다시 실행하는 작업은 별도다. 새로고침 후에는 최근 기록에서 기존 테스트의 로그를 확인한다. 실제 재발송을 원할 때만 **새 테스트 준비**에서 기기를 다시 조회하고 새 요청을 확인한다. 기존 테스트의 전달 결과가 불명확한 상태에서 새 테스트를 만들면 알림이 두 번 도착할 수 있다.

## 기존 DLQ replay 도구의 제한

`apps/worker/cmd/dlq`에는 replay 명령이 있지만, 현재 구현을 일반 콘솔의 재발송 버튼에 바로 연결하면 안 된다.

- 단일 idempotency key 조회는 tenant 필터가 없고, 완료된 replay를 다시 선택할 수 있다.
- 대상 조회와 replay 표시 사이에 동시 실행을 막는 원자적 claim이 없다.
- 멱등 상태를 지운 뒤 발행하므로 장애 시 상태 복구가 필요하다.
- 모든 envelope를 `send.push`로 발행한다. 이메일·알림톡 DLQ까지 일괄 재발행하면 잘못된 채널로 간다.
- 원본 토큰·본문을 재사용한다. 현재 토큰, 고객 삭제, 동의 철회, 저니 중지·만료 여부를 미리 검증하는 콘솔용 심사가 없다.

따라서 이번 작업에서 이 명령으로 실제 메시지를 재발송하지 않았다. `--all`은 일반적인 복구 절차로 권장하지 않는다.

## 콘솔 재발송을 위한 다음 구현

1. 실패 조회 API에서 최신 상태와 DLQ 존재 여부를 결합한다. `failed` 이후 성공한 메시지, 제공자 접수 결과 불명확, 이미 처리 중인 항목은 기본 재발송 대상에서 제외한다.
2. 원인별 판정: 일시 오류·429는 자동 재시도 진행 여부부터 확인; 인증 오류는 채널 수정 후 재검증; 만료·무효 토큰은 새 토큰 등록 후 검증; 권한 거부·동의 철회·삭제 고객은 제외. 빈도 제한·조용한 시간으로 건너뛴 항목은 실패로 취급하지 않는다.
3. 테넌트·앱에 한정한 미리보기 API가 대상 수, 제외 사유, 원본 발송 시점과 내용, 채널을 보여준다. 원본 payload 보존 기간이 지나면 재발송 불가로 표시한다.
4. 권한 있는 운영자가 한 건 또는 명시적으로 선택한 항목을 확인한다. 요청 UUID와 원본 메시지 ID를 unique하게 저장하고, DB transaction으로 재발송 claim과 채널별 outbox를 생성한다. Redis의 기존 성공 멱등 키를 지우지 않는다.
5. 새 시도 ID를 원본 메시지에 연결하고 actor·사유·요청 시각·결과를 감사 기록에 남긴다. 새 시도도 현재 고객 상태와 채널 정책을 워커에서 재검증한다.
6. 제공자 접수 직후 연결이 끊긴 경우 정확히 한 번 전달을 보장할 수 없다. 제공자 조회/receipt로 해소 가능한 항목은 먼저 조회하고, 해소 불가 항목은 중복 위험을 별도로 확인하도록 한다.

수용 테스트: 다른 테넌트 접근 차단, 권한 없는 호출 차단, 동시 재발송 하나만 접수, 응답 유실 복구, 성공 이력 재발송 제외, 삭제/동의/토큰 변경 재검증, 채널별 라우팅, 중간 장애 복구, 원본↔새 시도 추적.

## 배포 순서

`0009_test_push_runs.sql`을 공식 migrator로 먼저 적용한 뒤 API를 배포한다. API readiness는 새 테이블이 없으면 실패한다. 콘솔은 갱신된 API client와 함께 빌드한다. 테스트 접수는 기존 `journey_outbox`를 사용하므로 **outbox relay를 실행하는 `scheduler` 또는 `all` 역할의 워커가 있어야 큐로 발행된다**. 채널 워커와 제공자 접수·실제 기기 수신은 별도 검증한다.

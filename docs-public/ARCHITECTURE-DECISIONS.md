# 아키텍처 결정 기록 (ADR)

"왜 이 기술인가"에 대한 답이다. 각 항목은 **결정 · 근거 · 검토한 대안 · 재검토 조건**을 적는다.
재검토 조건은 결정이 틀린 게 아니라 **전제가 바뀌었는지**를 보는 기준이다 — 전제가 바뀌면 이 문서부터 고친다.

코드 대조 기준일: 2026-09-07. 스프린트 원장의 ADR-1~8(큐·프레임워크·마이그레이션 등)은 내부 문서에 있고, 여기는 외부에 설명해야 하는 결정만 둔다.

---

## ADR-0. 저장소를 둘로 나눈다 — PostgreSQL(현재 상태) + ClickHouse(일어난 사실)

### 결정

| | PostgreSQL | ClickHouse |
|---|---|---|
| 담는 것 | **현재 상태** — 테넌트·앱·암호화 크리덴셜·사용자·디바이스·저니 정의·저니 진행 상태·outbox·DLQ·세션 (26개 테이블) | **일어난 사실** — 수집 이벤트, 발송 원장(`message_log`), 도달·열림(`message_lifecycle`), 집계 뷰 |
| 쓰기 패턴 | 행 하나를 **갱신** — 상태 전이, 락, 유니크 제약 | **추가만** — 수정·삭제 없음 |
| 읽기 패턴 | 기본키로 한 행 | 테넌트·기간으로 **수천만 행 집계** |
| 크기 | 작다 | 크다 — 이벤트 수집량이 곧 데이터 크기 |

### 근거 (코드에서 확인 가능한 것)

- **정확히 한 번 발송**은 PG의 트랜잭션 기능에 기댄다. 멱등 upsert(`ON CONFLICT`) 21곳, outbox 릴레이의 `FOR UPDATE SKIP LOCKED` 4곳. ClickHouse에는 유니크 제약·행 잠금·트랜잭션이 없어 이 역할을 맡길 수 없다.
- **세그먼트 카운트는 컬럼 스토어 쿼리다.** `apps/worker/internal/segment/compiler.go`는 세그먼트 조건을 ClickHouse SQL(`uniqExact`, 기간 집계)로 컴파일한다. "지난 30일에 이벤트 X를 3회 이상 한 사용자"를 수천만 행에서 세는 일은 행 저장소의 인덱스·VACUUM이 먼저 무너지는 지점이다.
- **두 워크로드를 한 저장소에 두면 서로를 해친다.** 대량 append가 상태 테이블의 캐시와 WAL을 밀어내고, 집계 쿼리가 발송 트랜잭션의 지연을 키운다.

### 검토한 대안

| 대안 | 결론 |
|---|---|
| **PostgreSQL 하나로** (파티셔닝·TimescaleDB) | MVP 규모에서는 **충분히 가능하다.** 운영 컴포넌트 하나를 덜고 백업·업그레이드가 단순해진다. 채택하지 않은 이유는 세그먼트·리포트 쿼리를 나중에 전부 다시 써야 하는 이관 비용이고, 이 제품의 핵심 약속이 "실시간 세그먼트"라서 처음부터 컬럼 스토어에 뒀다. **이 선택이 지금 규모에서 과하다는 지적은 타당하다.** |
| **MySQL / MariaDB** (PG 대신) | **가능하다.** 결정적 차이는 없고 PG가 더 편한 지점이 있을 뿐이다: 스키마의 JSONB 19개(프로필 속성·저니 정의·세그먼트 필터)에 대한 인덱싱·연산자, ENUM 16개·UUID·배열·partial index, `ON CONFLICT DO UPDATE`의 예측 가능한 의미, pgx 등 Go 생태계. 반대로 한국 기업 다수가 MySQL을 운영하고 있어 셀프호스팅 도입 마찰은 MySQL이 낮았을 수 있다. |
| **ClickHouse 하나로** | 불가. 상태 갱신·제약·잠금이 없다. |
| **MongoDB** | 상태와 사실 어느 쪽에도 최선이 아니다. 집계는 CH에, 제약은 PG에 진다. |

### 재검토 조건

- 이벤트 총량이 **1년 뒤에도 수천만 행 미만**이면 → PG 단일 저장소로 되돌리는 것을 검토한다. 이관 대상은 `db/clickhouse/*.sql`의 테이블과 `segment/compiler.go`의 쿼리 생성기다.
- 관리형 ClickHouse(Cloud)를 쓰는 배포가 다수가 되면 → 셀프호스팅 CH 운영 문서를 줄인다.
- 세그먼트 실시간성 요건이 "분 단위 지연 허용"으로 완화되면 → PG 배치 집계가 후보가 된다.

## ADR-0b. Redis는 큐이자 상태다 — 그리고 그게 약점이다

### 결정

Redis Streams를 큐 브로커로 쓰고(내부 ADR-1), 같은 Redis에 발송 멱등 키·재시도 카운터·중복 억제·빈도 제한을 둔다.

### 근거

스택에 이미 Redis가 있고(API 레이트 리밋이 쓴다), TS 생산·Go 소비 양쪽에 1급 클라이언트가 있으며, Consumer Group의 ack/claim으로 at-least-once가 된다. NATS는 운영 컴포넌트 추가, Kafka는 MVP 과설계로 봤다. 큐 접근은 `libqueue`(TS/Go 쌍둥이)로만 하도록 CI가 강제해서 Kafka 이관 시 교체 지점이 하나다.

### 알고 있는 약점

- `MAXLEN ~ 1,000,000`은 배압이 아니라 **오래된 항목 트림**이다. 소비가 밀리면 조용히 사라진다. `nudgeon_queue_group_trim_loss` 지표와 경보로 관측한다.
- Redis를 잃으면 큐만 잃는 게 아니라 **"이미 보냈는지"를 잃는다** → 중복 발송. AOF `everysec`로 최대 1초 창을 허용하고, 사후 대사는 [Redis 유실 대응 런북](REDIS-RECOVERY-RUNBOOK.md)의 `cmd/reconcile`이 맡는다.

### 재검토 조건

- 큐 트림 경보가 실제로 울리기 시작하면 → Kafka/NATS JetStream 이관. `libqueue` 교체로 끝나야 하며, 그렇지 않다면 규칙 2가 뚫린 것이다.
- 멱등 키를 Redis 밖(PG `message_log` 선기록)으로 옮기면 Redis 유실이 중복 발송으로 이어지지 않는다. 발송 지연이 늘어나는 대가가 있다.

---

## 이 문서를 고쳐야 할 때

- 재검토 조건 중 하나가 충족됐을 때 — 결정을 바꾸지 않더라도 "검토했고 유지한다"를 날짜와 함께 적는다.
- 위 근거의 숫자(테이블 수, `ON CONFLICT` 개수 등)가 크게 달라졌을 때.
- 투자자·기여자에게서 같은 질문을 두 번 받았을 때 — 그 질문이 곧 빠진 항목이다.

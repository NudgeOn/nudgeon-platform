# Local operations audit harness

This is a bounded, single-machine audit, not a production benchmark or a
24-hour soak. It never uses provider credentials or creates cloud resources.
The API and worker have no external network route. Only the fixed-target
gateway joins a host-access network; its published ports bind to loopback.

## Scope and safety

- Dedicated project: `nudgeon-local-ops-20260903a`; existing projects are untouched.
- Test-only database password and master key are intentionally non-secret.
- CPU/memory limits apply to the new containers. Load stops if sampled total
  Docker container memory exceeds 7.1 GiB. Sampling is not a hard VM memory cap.
- Each track request contains one event and creates new anonymous/device IDs.
  This stresses new-user writes, not a representative returning-user mix.
- API acceptance, PostgreSQL receipts/projection, and ClickHouse event IDs are
  reconciled per run. HTTP timeouts can be ambiguous in general; receipts are
  checked independently rather than assuming a timeout means no write.
- Alert tests use a deliberately corrupt local credential and seed four prior
  attempts. The actual worker performs the final failure and writes the DLQ.
  This does not prove real provider delivery or natural retry timing.
- Backup runs after API/worker shutdown. PostgreSQL dump, ClickHouse native
  backup, and Redis RDB are restored into separate, initially empty volumes.
  It is a quiesced local restore, not live PITR or a managed-database failover.
- Tests retain evidence and stopped volumes. They do not delete user data.

## Commands used for this audit

Run from the platform repository root. The fixed project and backup name are
single-use: do not rerun backup/restore over existing audit state. For a new
audit, choose a new project in `run.mjs` and matching Compose `-p` argument;
stop this audit's containers first to release the fixed loopback ports.

```sh
export OPS_MASTER_KEY=AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=
loadgen_dir=$(mktemp -d /tmp/nudgeon-local-ops.XXXXXX)
GOCACHE=/tmp/nudgeon-go-build-cache go build -o "$loadgen_dir/loadgen" ./apps/worker/cmd/loadgen
export OPS_LOADGEN_BIN="$loadgen_dir/loadgen"

docker compose -p nudgeon-local-ops-20260903a -f tests/ops/local/compose.yaml up -d gateway postgres clickhouse redis migrator api worker
node tests/ops/local/run.mjs ramp
node tests/ops/local/run.mjs recovery
docker compose -p nudgeon-local-ops-20260903a -f tests/ops/local/compose.yaml --profile alerts up -d dlq-monitor receiver prometheus alertmanager
node tests/ops/local/run.mjs alerts
node tests/ops/local/run.mjs stability
node tests/ops/local/run.mjs metadata
node tests/ops/local/run.mjs backup
node tests/ops/local/run.mjs restore
node tests/ops/local/run.mjs stop
```

A failed ramp stops escalation; it must not be overridden to claim the next
rate passed. The audit may continue with independent recovery/alert tests.
`stability` runs 100 requests/s for five minutes. It is intentionally **not**
24 hours. The load generator now uses bounded histograms, but this harness still
loads database IDs into memory and lacks 24-hour disk/VM preflight and M0/M1
workload profiles. No longer-duration qualification is implied.

The runner passes its synthetic key over stdin (`--key-file -`) and stores a
fresh `loadgen-<run-id>/` evidence directory. It reads the JSON summary rather
than parsing translated console labels. Missing/incomplete summaries fail the
run. Historical logs and database backups are not regenerated by these changes.
See the [load generator guide](../../../apps/worker/cmd/loadgen/README.md).

Evidence is under ignored `.nudgeon/nudgeon-local-ops-20260903a/`. Do not commit
`credentials.local.json` or database dumps. Image IDs and source hashes are in
`metadata.json`; application image tags are existing local builds, not a fresh
build automatically performed by this harness.

The updated alert configuration requires the new `dlq-monitor` worker role and
the additive `resolved_at` schema migration before running the alert profile.
Do not reuse old worker images or migrate the retained historical audit DB just
to reproduce that old report. Use a new project with compatible fresh images
and schema, or the [isolated DLQ regression](../dlq/README.md), which compiles and
mounts the observer/CLI without replacing the existing image tags.

`loadgen_transport_probe_test.go` is a diagnostic overlay for the real
`cmd/loadgen` package, not a standalone Go package. The September 3 audit used
`/tmp/nudgeon-local-ops.3n60wf/transport-overlay.json` to map it to
`apps/worker/cmd/loadgen/local_ops_transport_test.go`, then ran:

```sh
GOCACHE=/tmp/nudgeon-go-build-cache go test -overlay=/tmp/nudgeon-local-ops.3n60wf/transport-overlay.json ./apps/worker/cmd/loadgen -run '^TestLocalOpsTransportReusesHTTPConnection$' -v -count=1
```

The probe expects one TCP connection for ten sequential successful requests.
It failed against the original audited implementation because response bodies
were closed without being consumed. `TestHTTPConnectionReuse` now includes the
same check in the ordinary `cmd/loadgen` suite, with no overlay needed:

```sh
go test ./apps/worker/cmd/loadgen -run '^TestHTTPConnectionReuse$' -v -count=1
```

# 교차 테넌트 격리 스위트 (M-6 / T-8)

테넌트 A의 세션·키로 테넌트 B의 리소스에 접근하면 전부 403/404여야 한다 (PRD-06 8장).

```bash
# 사전: docker compose --profile full --profile app 기동 (MODE=multi_tenant)
node tests/isolation/run.mjs
node tests/isolation/routes.mjs apps/api/src   # 컨트롤러에서 뽑은 라우트 목록만 보기
```

## 어떻게 "전수"인가

- 대입 경로는 손으로 적은 목록이 아니라 **컨트롤러 소스의 데코레이터에서 뽑는다**(`routes.mjs`). 새 엔드포인트는 자동으로 포함된다. 동적 등록 라우트는 못 잡는다.
- 경로 파라미터는 B가 **실제로 가진 리소스 id**로 채운다(세그먼트·저니·이메일 템플릿·알림톡 발신프로필·키·유저·멤버). 그래야 404가 격리 때문인지 원래 없어서인지 구분된다. 못 만든 리소스는 `?`(미확정)로 표시한다.
- **400도 위반이다.** NestJS는 가드가 파이프보다 먼저 돌므로, 타 테넌트 호출에 400(검증 오류)이 오면 접근 검사가 본문 검증 뒤에 있다는 뜻이고 필드명이 새어 나간다.
- 서버 키 경로(`DELETE /v1/users/:externalId`)는 상태 코드가 아니라 **B의 유저가 남아 있는지**로 본다(키는 자기 앱에만 묶이고 삭제는 비동기 202).
- 대조군: B 자신은 자기 저니를 200으로 읽어야 한다 — "전부 404"로 통과하는 스위트를 막는다.

## 2026-09-10 실행

컨트롤러 85개 라우트 중 앱/멤버 범위 55 + 서명 없는 웹훅 1 = 56개 경로, 서버 키 삭제 1, 대조군 1 → **위반 0, 미확정 0**.

첫 실행에서 위반 5건이 나왔고 4건을 고쳤다(1건은 프로브 오판):
- `PUT /apps/:appId/settings`, `POST …/test-email`, `POST …/test-push`, `PATCH /members/:memberId/role` — 본문 검증이 소속 확인보다 앞에 있어 타 테넌트 호출자에게 400과 필드명이 갔다. 소속 확인을 앞으로 옮겼다.
- `DELETE /v1/users/:externalId`(A 서버 키)의 202는 A 앱 범위의 비동기 접수였고 B의 유저는 남았다.

종료 코드 0 = 전 경로 격리, 1 = 위반 발견.
